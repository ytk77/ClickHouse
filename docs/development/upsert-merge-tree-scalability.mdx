# `UpsertMergeTree` scalability {#upsert-scalability}

This work targets the overhead of retaining many live rows and parts. It does not establish a 10-billion-row capacity or latency guarantee. The evaluation uses a bounded wall-clock budget and independently varies live rows, active parts, update distribution, and concurrent readers.

## Incremental publication {#incremental-publication}

`PartCatalog` is an immutable AVL tree ordered by `MergeTreePartInfo`. Adding or retiring a part copies the affected search paths, rather than enumerating the native active-part set. Nodes aggregate the minimum metadata/data versions, partition boundaries, and lightweight-delete flag. Column and index sizes continue to use incremental accounting. Publication returns the old snapshot to the caller, which retains it in a local variable declared before the parts lock. Cached full ranges and partition-version maps are therefore released after unlocking, including during exception unwinding. At most one retired root is held per committing operation; there is no retirement queue.

A query owns the catalog root and its matching visibility snapshot. When a partition predicate is available before materialization, entire subtrees belonging to a pruned partition are skipped. Full materialization is cached per catalog root and reused by readers; it happens outside the writer's parts lock. A full-table query still enumerates its selected parts. Native `data_parts_indexes` and the catalog remain proportional to the active-part count; this is not disk-paged metadata.

Partition data-version maps are initialized lazily once per immutable root and shared directly by queries. The first query after publication may still pay O(selected parts) range-materialization cost; other readers can wait on that root's materialization mutex.

Maintenance traverses at most 256 new candidates per tick from the native ordered index, plus at most one small candidate carried across a scan boundary. Its cursor advances over healthy and oversized parts as well as candidates selected for rewriting. This removes full-table candidate copying and traverses a finite backlog in rounds. A continuously growing hot partition can still delay later partitions when ingestion outpaces maintenance. It does not provide a fixed TTL latency independent of the number of parts, nor a priority scheduler for compaction debt. A complete idle scan backs off from 1 second to at most 30 seconds. A healthy cycle with new publications uses a 1-second cooldown before another full scan; an in-flight notification can request an earlier pass. Publications and schema changes wake an idle task. Tables with any TTL retain a maximum 1-second idle delay, including while TTL merges are stopped; this bounds the extra delay when time advances or TTL merges restart. Completing a cycle can still require multiple slices and rewrites. Even without rewrite work, a full pass needs roughly `ceil(P / 256)` ticks, normally spaced 100 ms apart, plus scheduling/lock wait time. TTL expiration therefore has no fixed 1-second completion guarantee; actual rewrites, throttling and contention can extend the delay substantially. Candidates that exceed the current unit budget remain ahead of the cursor for the next tick; carried candidates never move the cursor backwards.

A maintenance `CORRUPTED_DATA` exception fences the table, increments `UpsertMaintenanceCorruptionFailures`, and logs the phase, candidate part when available, and cause. `UpsertMaintenanceFailures` also counts other maintenance exceptions. It does not repeatedly retry a corrupt candidate while silently preventing later parts from progressing. While fenced, TTL maintenance and new reads/writes stop. Restart repeats metadata verification, with full payload verification in the background or before destructive source use. A successful attach alone does not certify payload integrity; actual corruption must be repaired before that payload can pass verification.

## Visibility cache {#visibility-cache}

The disk-state instance owns a byte-bounded cache of immutable decoded masks. Its keys contain the part object identity and an in-memory mask generation. An immutable version map is published with each pinned `RocksDB` snapshot; unchanged masks retain their generation across commits. Mask-write helpers record an ordered change list alongside the state batch, including retirement and `TRUNCATE` range deletion. Publication applies only that list; debug builds cross-check it against the actual batch before writing.

Recovery reconstructs the version map after validating the durable authority. Cache contents and generations are not persisted and cannot change winner decisions. Independent database instances have independent caches. Eviction releases the cache's reference; readers may retain an evicted bitmap until their query ends, so the configured cache size is not a total query-memory limit.

## Resource settings and recovery {#resource-settings}

All settings have defaults. Ordinary `CREATE TABLE`, `INSERT` and `SELECT` require no additional database or session settings. These resource settings are captured when a table opens; changing them with `ALTER` is not supported.

| Setting | Default | Meaning |
| --- | --- | --- |
| `upsert_index_cache_bytes` | 64 MiB | Per-table `RocksDB` block-cache capacity |
| `upsert_mask_cache_bytes` | 32 MiB | Retained decoded-mask cache; zero disables it |
| `upsert_write_buffer_bytes` | 16 MiB | Size of a write buffer |
| `upsert_write_buffer_count` | 3 | Maximum write-buffer count |
| `upsert_wal_bytes` | 64 MiB | WAL size threshold for flushing |
| `upsert_background_jobs` | 2 | `RocksDB` background-job budget |
| `upsert_max_open_files` | 128 | `RocksDB` open-file budget |
| `upsert_partitioned_filters` | true | Partitioned index and Bloom-filter blocks |
| `upsert_recovery_threads` | 4 | Maximum outstanding startup-verification workers |

These are performance budgets, not changes to synchronous durability. WAL flushing thresholds and cache capacity are not hard limits on all process memory or disk use. Resources across multiple tables must still fit the server's capacity. Default cache capacities plus configured write buffers total approximately 144 MiB per table; this is potential configured consumption, not a claim that all those bytes are always resident. It also excludes other memory such as part metadata and query buffers. **A multi-table sharding rollout requires an explicit aggregate resource budget; this implementation supplies no server-wide cache or memtable quota.**

Explicit `upsert_*` settings on other `MergeTree` engines are rejected by `CREATE` and `ALTER MODIFY SETTING`. Inherited server defaults do not trigger that rejection. Existing non-upsert metadata containing such settings remains attachable, with a warning that the settings are ignored.

The resource validator identifies the invalid setting, value and allowed range. `upsert_max_open_files` accepts 20 through 2,147,483,647; the `RocksDB` value -1 (unlimited) is not supported. Server `<merge_tree>` defaults are read when a table opens; updating them does not resize an already-open table's resources. Reopening applies the defaults, except where explicit table settings override them.

The durable state format is unchanged, but table metadata containing new explicit settings is not understood by older binaries. Those tables cannot simply be attached after downgrade. `ALTER RESET SETTING` is currently unsupported on `UpsertMergeTree`; do not assume it can remove this compatibility barrier. Validate a data migration to an older-compatible table definition before downgrading.

Recovery verifies every authorized part's authenticated inventory, file names and sizes, metadata contents, and visibility mask before publishing the table. Full hashing of column and lineage `.bin` files and `unique_key_index.sst` is deferred to a separate background sweep or destructive source use. Parts without a persisted inventory, and authorized temporary parts awaiting rename, still require full startup verification. The startup queue is bounded by `upsert_recovery_threads`; all workers finish before native loading. A startup verification exception fails recovery.

### Staged payload verification {#staged-payload-verification}

Ordinary `SELECT` queries, including projection selection and `mergeTreeProjection` introspection, check the sticky verification failure state without hashing whole parts or waiting for a background payload-verification mutex. Reads use native compression checksums for the blocks they consume. This does not authenticate unread columns, or prove that a structurally valid substituted payload matches its original commit. Queries can return results before the background sweep detects such damage. A failure rejects subsequent reads and writes; it does not cancel queries already in flight.

Maintenance rewrites and partition operations retain full source verification before consuming or exporting recovered payloads, preventing corrupted sources from being reauthorized as new outputs. `DiskState::loadPartRows` also authenticates the exact `upsert_rows.bin` bytes passed to `decodePartRows` against the committed inventory on every use, including newly committed and previously verified parts. It then checks the envelope CRC, row offsets, row count and lineage. Survivor parts used only to restore winners in cleared partitions follow this lineage-only path because their columns are not consumed or rewritten. This bounded read does not acquire the background verification mutex or complete the pending full verification obligation. A missing or mismatched inventory or sidecar raises `CORRUPTED_DATA` and fences the state; transient file-open/read exceptions propagate without setting that fence. New parts remain fully authenticated and synchronized before their durable authorization.

Startup hashes `upsert_ttl.txt`, `ttl.txt` and `checksums.txt`; maintenance uses the policy checksum and TTL information loaded from this authenticated metadata. Winner lookups use the state database. New parts omit the redundant `unique_key_index.sst`; existing parts retain it, and the full sweep authenticates its contents. A future consumer must validate its committed inventory entry before use.

A dedicated background task starts after one second, pins and verifies one active part per slice outside the parts lock, and waits 100 ms between slices. After a complete pass it waits 24 hours before starting another full sweep. The task shares the table operation mutex with schema and partition operations. One large part can therefore delay those operations and shutdown; ordinary inserts do not take that mutex. The task has no separate byte-rate limit, and hashing competes with query and write I/O. Continuous ingestion can extend a sweep; the interval is not a deadline for detecting corruption.

A payload verification failure is sticky for that open and rejects subsequent reads and writes. An attach that succeeds with deferred payloads is not proof that those payloads are intact. While recovered payloads remain pending, superseded sources found at startup are retained outside native part loading, and consumed detached inputs remain unavailable for reuse. Cleanup resumes only after pending verification is complete or the corresponding active data is explicitly retired. The verification map is bounded by the number of parts present at open, including entries required by old pinned snapshots; it does not grow with subsequent inserts.

Existing disk-state tables need one full startup scan to establish missing inventories. Later starts avoid bulk payload hashing, but still enumerate every file, read metadata, validate masks, and load native part metadata. This does not remove part-count overhead or establish a startup speedup without workload measurements. See [disk-state recovery](/development/upsert-merge-tree-disk-state#disk-state-staged-recovery) for persistence and cleanup details.

## Query part size and cache prewarming {#query-part-size-prewarming}

`UpsertMergeTree` stores ordinary column-oriented `MergeTree` parts. A small whole-row byte target can nevertheless produce many parts on a wide table, even when a query reads only two columns. Every selected part adds file, mark-loading and scheduling work. Compare identical queries and data on the same host with matched cache states before attributing a latency difference to the engine.

`upsert_maintenance_target_bytes` controls background source selection and the output byte target. The default is 4,294,967,296 bytes (4 GiB); the supported range is 32 MiB through 8 GiB. Explicit table settings and server `<merge_tree>` defaults override this compiled default. Physical parts are limited to 268,435,456 rows and 2 GiB of lineage. Winner relocation commits in independent bounded batches; the 128-MiB state-batch limit no longer limits physical part size. This setting does not enlarge insertion units or foreground mutation output. Maintenance uses version-2 payload authorizations and `UMPROW02` for large lineage sidecars; small sidecars retain `UMPROW01`. `Native` column serialization is unchanged. Atomic partition imports keep their 128-MiB state limit; a sufficiently large detached part can exceed it and be rejected without changing the detached payload. Complete table backups must include matching engine state. Older binaries cannot read these new authorizations, so reverting requires restoring a pre-upgrade backup rather than reopening newly compacted state.

```sql
ALTER TABLE events MODIFY SETTING
    upsert_maintenance_target_bytes = 1073741824,
    prewarm_mark_cache = 1,
    columns_to_prewarm_mark_cache = 'AFFILIATE,USER_ID';
```

The setting above and `prewarm_mark_cache`, `prewarm_primary_key_cache`, `columns_to_prewarm_mark_cache`, and `min_bytes_to_prewarm_caches` can be changed with a settings-only `ALTER TABLE ... MODIFY SETTING`. Resource settings in the preceding table remain open-time settings. `RESET SETTING` remains unsupported; explicitly assigning 33,554,432 sets the target back to 32 MiB, rather than restoring inheritance from server defaults. Metadata containing the new setting requires a binary that recognizes it.

Insertion has a separate, alterable `upsert_insert_target_bytes` setting, defaulting to 512 MiB
and accepting up to 1 GiB. A larger target allows wider input blocks to produce larger parts
before background maintenance. The sink does not accumulate separate blocks; its 1,048,576-row,
64 MiB lineage and 128 MiB atomic state-batch bounds still apply. One preparation above the
128 MiB pending-column budget runs alone within its sink, and query memory limits still apply.
Keep the target and block boundaries unchanged for token-based retries. See
[configurable insert units](/development/upsert-merge-tree#configurable-insert-units).

Changing the target wakes maintenance and revisits existing parts. Convergence requires multiple cycles and additional rewrite I/O. The settings operation waits for an active rewrite under the operation mutex; that wait has no separate `lock_acquire_timeout`. A failed metadata operation leaves the table usable only when the old metadata can be verified unchanged. A failure after replacement, or an uncertain metadata state, fences the table until restart and full recovery.

Rewrite memory is not limited to the target: input columns, filtered copies, output and rebuilding an overflowing prefix coexist. Peak memory can be several times the target (roughly 2–3 times for these buffers, plus writer and state overhead). Background work does not inherit the client's query memory limit. Concurrent maintenance across tables requires a server memory budget. Longer rewrites also retain source parts longer and temporarily increase disk use.

An in-memory hint records background physical output cut by a byte, row or lineage budget. At the same or a smaller target, healthy compaction skips that part; expiration, stale TTL metadata and at least 25 percent masked rows still trigger rewriting. This prevents endless rewrites caused by differences between serialized and in-memory column sizes. Raising the target or changing the schema allows reconsideration. Retired-part hints are removed. A hint is published only when relocation of its physical output is complete; partially relocated outputs have no hint. A completed intermediate output and its hint remain valid if a later output fails or stops for a changed TTL policy; the source stays active with the already moved rows masked. Hints disappear on reopen, so restart can cause additional compaction before convergence. A hinted part with less than 25 percent masked rows can retain that unused space until another rewrite condition applies. `UpsertMaintenanceSaturatedSkips` counts these scheduling skips.

Insertion, background rewrite and partition import prewarm caches after successful publication and outside the parts lock, using the existing temporary writer's retained marks. Wide parts honor the configured column filter; Compact parts keep a single marks file for all columns, so the column filter does not apply. Prewarming remains disabled by default and respects the minimum-size setting. A cache-fill failure is logged and counted without changing an already durable commit result. `UpsertPartCachePrewarms` counts eligible successful prewarm calls, not marks inserted: a part whose writer started before prewarming was enabled may have no retained marks. `UpsertPartCachePrewarmFailures` counts exceptions. Prewarming addresses mark loading; it does not warm all column data pages.

### Background rewrite admission and write amplification {#background-rewrite-admission}

The compiled target is 4 GiB. Healthy compaction requires comparable source sizes:
when extending a run, neither the accumulated prefix nor the next candidate may exceed four times
the other. An incompatible healthy singleton is deferred so newer small parts can merge with each
other first. A ready run is processed before reconsidering the next candidate. Expired rows, stale
`TTL` policy and at least 25 percent masked rows can trigger a singleton rewrite and never require
a size-matched partner. Such a source does not make unrelated, disproportionate healthy neighbors
eligible for the same run. This trades some
additional active parts and slower convergence for less repeated copying during small-batch ingestion.
A quiet table may retain a sequence such as 100/20/4/1 MiB rather than repeatedly copying its largest part.

Two server settings, read at startup, bound background rewrite admission:

| Setting | Default | Meaning |
| --- | ---: | --- |
| `max_concurrent_upsert_maintenance_rewrites` | 2 | Concurrent background rewrite attempts across tables |
| `upsert_maintenance_memory_budget` | 2 GiB | Soft budget for estimated memory reservations of admitted attempts |

Both must be positive. Reservations estimate three times the smaller of the target and selected
sources' total uncompressed on-disk bytes, plus the largest source, source and output lineage, row metadata, relocation maps,
and estimated state work capped at half the state-batch limit. The reservation doubles this sum to allow for additional native sorting and temporary copies.
Small rewrites therefore do not reserve an entire target-sized buffer. A single attempt exceeding the reservation budget may run alone when
background and server headroom permit it; `UpsertMaintenanceOversizedAdmissions` records this policy.
Admission also checks the background merge soft limit and server memory hard limit, using their
current tracked usage plus reservations. This intentionally counts some active allocations twice.
Reservations are estimates, not allocator caps or an out-of-memory guarantee: defaults, dictionaries,
projections and writer buffers can change actual usage. Active rewrites use the ordinary background
merge memory tracker and remain subject to the server memory limit.

A cheap admission precheck runs before cleanup or candidate scanning. Deferrals at this point have a
separate counter and do not produce denial warnings, because the table may be idle. They preserve an
existing longer idle delay (up to 30 seconds) when no new publication has occurred. A task denied admission releases
its locks and retries after 1, 2, 4, 8, then 10 seconds, plus a stable table-specific offset of up to
250 milliseconds. If selection has already run, its cursor and carried candidate are restored.
Notifications cannot bypass this retry deadline. Denials are logged at consecutive counts of 1, 2, 4,
8 and so on. Admission uses polling rather than a FIFO queue, so strict fairness is not guaranteed.
It does not wait for a rewrite slot on a worker thread. A task also reschedules if a foreground
operation holds the table operation mutex. An admitted rewrite still runs on a background schedule
pool worker; this change does not move rewriting to a dedicated executor. Admission limits do not
cover foreground mutations, partition imports or retirement cleanup.

`MEMORY_LIMIT_EXCEEDED`, `CANNOT_ALLOCATE_MEMORY`, and allocation exceptions trigger a per-table monotonic-clock retry deadline of 1, 2, 4, 8, 16, 32,
then 60 seconds. New publications cannot bypass that deadline. A successful rewrite resets the delay.
The setting remains unchanged. Before selection, maintenance derives one effective target from the
lower positive background soft memory limit and server hard memory limit. It halves the configured
target until ten targets fit that ceiling, with a 32-MiB floor, and logs the resulting byte target.
The same effective target controls healthy-part skips, source accumulation, output splitting and
saturation hints. Actual source row and lineage density is checked separately and can keep parts
smaller. For example, with a 16-GiB ceiling the configured 4-GiB target becomes 1 GiB; with a
32-GiB ceiling it becomes 2 GiB. These are configured-limit calculations, independent of temporary
memory use, so output parts are not repeatedly split and reselected as pressure fluctuates.

Temporary headroom denials preserve the selection cursor and retry. A source whose fixed lineage
and input estimate cannot fit the configured ceiling is reported and skipped, allowing other parts
and partitions to progress. Its expiration and dead-row cleanup remain pending until limits grow;
this implementation still loads whole-source lineage. Resource pressure can delay `TTL` cleanup.
The size-ratio rule itself never suppresses an expired source.

Foreground operations signal while waiting for the operation mutex. Background maintenance yields
at source-read, block and pre-write boundaries; if no output committed, it restores its cursor and
retries after one second. It does not preempt a running native writer or interrupt relocation of an
already written output. Continuous foreground traffic can postpone maintenance; the yield counter
includes precheck deferrals. Immutable lineage loading and the final winner assertion scan run
outside the parts lock, while source retirement checks full masks and authenticated identities under
the lock. The assertion scan does not populate the winner block cache.

The sequential source reader already uses `max_merges_bandwidth_for_server` for local and remote
column-data reads. This is not a complete rewrite-I/O limit: output writing, lineage reads, payload
hashing and synchronization are not all charged to that throttler. No automatic upgrade ramp is
implemented. Before upgrading existing tables without explicit targets, administrators can retain
the previous 256-MiB target with `<merge_tree><upsert_maintenance_target_bytes>268435456</upsert_maintenance_target_bytes></merge_tree>`
and raise individual table targets gradually. Without an override, reopening adopts 4 GiB and can
initiate substantial compaction; the admission limits bound simultaneous work, not total rewrite bytes.
Both custom revisions report base version `26.8.1.1`; use `compatibility='26.8'` or an explicit target
to retain the deployed fork's 256-MiB behavior. `compatibility='26.8.1.1'` uses the new 4-GiB default.

Observability:

- `UpsertMaintenanceUnadmittableParts` counts sources skipped because their fixed estimate exceeds the configured ceiling.
- `UpsertMaintenanceYields` counts pending-foreground deferrals and pre-write yields.
- `UpsertForegroundOperationWaiters` in `system.metrics` counts foreground operations waiting for the operation lock across all tables; it drops when each operation acquires the lock.

- `system.metrics`: `UpsertMaintenanceRewrites`, `UpsertMaintenanceReservedBytes`, and
  `UpsertMaintenanceMemoryTracking` expose admitted attempts, reserved estimates and attributed allocations.
- `ProfileEvents`: `UpsertMaintenanceAdmissionPrecheckDeferrals`, `UpsertMaintenanceAdmissionDenied`, `UpsertMaintenanceSizeRatioSkips`,
  `UpsertMaintenanceMemoryBackoffs`, and `UpsertMaintenanceRewritesStarted` expose scheduling decisions.
  Candidate and skip counters include scans later deferred by admission and their retries; use actual
  rewrite/write counters to detect repeated rewriting, not candidate counts.
- `UpsertMaintenanceReadBytes` counts column blocks pulled using their in-memory `Block::bytes` size,
  including masked rows. `UpsertMaintenanceWrittenBytes` counts the same measure submitted to part writers before
  internal lineage columns are added. Both include work from failed attempts; neither measures physical
  device I/O. Compare written bytes against application insert-column bytes measured with the same
  in-memory representation over the same interval.
- `UpsertMaintenancePeakMemoryBytes` sums peak tracked memory across attempts. Divide by attempts for
  a mean of peaks; it is not a server-wide maximum or a latency percentile.

Foreground `DELETE` and schema/index rewrites still use 32 MiB output units, so they can split a larger
part and require later background compaction. Changing that path, mask-only expiration, vertical
rewriting and large-part activation require separate correctness and resource validation. These
admission and selection changes do not modify the durable format or the winner publication protocol.

The admission and size-ratio changes passed a Release compile/link and static review on 2026-10-02.
Functional, fault-injection and sustained-load tests of these changes have not yet run. Earlier test
counts and historical measurements below predate these safeguards and do not validate their benefit.
Follow-up evaluation should separate target and prewarming in a same-binary 2-by-2 comparison and
include sustained small inserts, hot-key overwrites, multiple tables converging together, memory
pressure, mixed-age `TTL`, and foreground deletes. Measure insert/query latency distributions,
rewrite bytes, admission denials and task memory peaks; no performance multiple is promised.

### Reproduce the wide-table comparison {#reproduce-wide-table-comparison}

`tests/integration/test_upsert_query_performance/benchmark.py` creates a fresh isolated loopback server and a 29-column table, inserts deterministic data, waits for compaction and executes the same `AFFILIATE` aggregation six times. Each invocation requires a new work directory. Run configurations sequentially, without concurrent builds or correctness tests:

```bash
python3 tests/integration/test_upsert_query_performance/benchmark.py \
    --binary build_release/programs/clickhouse \
    --work-dir tmp/upsert-query-128m \
    --log-dir build_release \
    --rows 5000000 --target-mib 128 --prewarm --seconds 900 \
    > build_release/test_upsert_query_128m.log 2>&1
```

Use `--legacy` with a baseline binary, `--target-mib 32`, `--target-mib 256`, and `--replacing` for the other configurations. Compare the generated `aggregate.tsv` files exactly. The synthetic version and key definitions match, allowing `ReplacingMergeTree FINAL` to serve as an oracle in this experiment. Production tables with different partition or ordering keys need a separate semantic comparison.

The first scan follows a file-local `POSIX_FADV_DONTNEED` request on this instance's own data/mark files; it is not a guaranteed disk-cold read. No shared-host kernel cache is cleared. Subsequent scans are warm samples. `results.json` records part counts, load/compaction times, query counters and server memory high-water marks. That high-water mark includes insertion and other server activity, so it does not isolate rewrite memory. A single trial per configuration cannot establish production tail latency or a promised speedup.

### Wide-table local results {#wide-table-local-results}

The 2026-10-02 comparison used five million deterministic rows, 29 columns, eight query threads,
a fresh local server per configuration and five warm samples. Runs were sequential without a
concurrent build or correctness suite. The baseline was `8ea965c973d`. All five aggregate outputs
matched byte for byte, including the matching-key `ReplacingMergeTree FINAL` oracle.

| Configuration | Active parts | First scan after file-local eviction | Warm median | Load | Compaction convergence |
| --- | ---: | ---: | ---: | ---: | ---: |
| Baseline, 32 MiB | 115 | 170.64 ms | 60.51 ms | 70.69 s | 16.52 s |
| Candidate, 32 MiB and prewarm | 115 | 130.33 ms | 58.67 ms | 58.01 s | 15.34 s |
| Candidate, 128 MiB and prewarm | 34 | 104.24 ms | 49.08 ms | 56.87 s | 75.39 s |
| Candidate, 256 MiB and prewarm | 15 | 93.61 ms | 56.95 ms | 57.13 s | 67.28 s |
| `ReplacingMergeTree FINAL` | 1 | 76.99 ms | 49.20 ms | 33.57 s | 24.39 s |

At the same 115 parts, prewarming reduced first-scan mark misses from 575 to zero, file opens
from 1,152 to 577, and aggregate mark-loading wait from 212,203 to 2,648 microseconds.
With 128/256 MiB targets, first-scan file opens fell to 172/77. OS-read bytes remained around
107–110 MB across upsert configurations: prewarming did not eliminate column-data I/O.
Process memory high-water marks were approximately 1.09/1.14/1.31 GiB for the three candidate
configurations, including insertion and all server activity; they are not isolated rewrite peaks.

These trials demonstrate fewer parts and lower first-scan overhead on this dataset. They do not
establish a 12-fold improvement or explain the complete cross-host production comparison. Warm
latency did not improve monotonically with target size. Larger targets required more compaction
time, and each configuration had only one load/convergence trial, so write-speed differences should
not be attributed to this change. These trials used the targets listed in the table; the compiled
default was subsequently increased to 256 MiB.

The first scan improved approximately 2.35 times, while warm latency was unchanged. Convergence

so its supplementary warm event medians use four records. The benchmark now waits for every
sample's log entry before completing telemetry collection.

## Measurements {#measurements}

`UpsertRecoveryMetadataParts` counts startup metadata verifications; `UpsertRecoveryParts` counts full startup verifications for legacy or temporary parts. `UpsertPayloadVerificationParts` counts successful destructive-source and background full verifications, and `UpsertPayloadVerificationMicroseconds` records their hashing time, including failed attempts. These are process-wide counters, not per-table pending-part gauges.

The `Upsert`-prefixed events in `system.events` and applicable query `ProfileEvents` distinguish winner lookup, mask loading/encoding, state preparation, synchronous state writes, insert commit-lock waiting/holding, snapshot construction, maintenance candidate visits, and recovery. `UpsertMaskCacheHits` and `UpsertMaskCacheMisses` describe decoded-mask reuse. Independent `CurrentMetrics` named `UpsertMaskCacheBytes` and `UpsertMaskCacheEntries` report retained upsert mask caches without combining them with the legacy unique-key cache. They aggregate all upsert tables, not individual tables. `UpsertCatalogVersionsMicroseconds` and `UpsertCatalogRangesMicroseconds` measure query-side map lookup/initialization and range selection/materialization, including wait time. `UpsertCatalogNodesAllocated` (named `UpsertSnapshotPartsVisited` in the initial evaluation logs) counts nodes allocated during tree construction, including balancing nodes; it is not the table's active-part count.

Use a baseline binary and the candidate with the same SQL, data, and settings. Record active parts and physical rows as well as latency: background maintenance can change these between runs. Small sample counts and concurrent build activity are insufficient for production tail-latency claims.

## Bounded acceptance stages {#bounded-acceptance-stages}

1. Validate overwrite, pinned snapshots, `DELETE`, `TRUNCATE`, schema operations, partitions, projections, and interrupted recovery.
2. Start with 1 million live rows. Increase to 10 million only while the time budget permits.
3. Independently create thousands of small parts to expose metadata costs without generating billions of rows.
4. Compare insert and overwrite duration, point/range queries, snapshot-work counters, physical/live row ratio, and recovery correctness.
5. Reserve time for failures and regression tests. Report incomplete or timed-out cases rather than extrapolating them to 10 billion rows.

Large physical parts, framed lineage, chunked durable masks, resumable many-to-one activation, group commit, and disk-paged metadata require separate protocol work. Staged verification adds an authenticated inventory to the state database while preserving existing part payloads and their authorization hashes. The larger architecture and migration requirements are described in [continuous ingestion](/development/upsert-merge-tree-continuous-ingestion).

## Reproduce the local evaluation {#reproduce-local-evaluation}

`tests/integration/test_upsert_scalability/benchmark.py` starts its own loopback server, creates a fresh data directory, checks row counts and query results, records per-query counters, and stops only that server. It refuses to reuse an existing work directory. Use different work directories for baseline and candidate runs, and run them sequentially without a concurrent build. Output and server logs belong in the build directory; runtime data and the detailed `results.json` belong under the repository's `tmp` directory.

```bash
python3 tests/integration/test_upsert_scalability/benchmark.py \
  --binary build_release_concurrency_clang21_norust/programs/clickhouse \
  --work-dir tmp/upsert-scale-candidate-1m \
  --log-dir build_release_concurrency_clang21_norust \
  --rows 1000000 --partitions 1024 --seconds 600 \
  > build_release_concurrency_clang21_norust/test_upsert_scale_candidate_1m.log 2>&1
```

The default ports are `19197` and `19198`; they can be overridden. The deadline bounds individual HTTP requests by the remaining budget, followed by at most 30 seconds for graceful server shutdown. This benchmark keeps normal background maintenance enabled and reports its resulting active-part count. It is not a fixed-part-count comparison or a production workload simulator.

Use `--restart` to compare row count and version sum after restarting. `--read-after-updates` also checks point and range query results against the generated update set. `--update-pattern hot` concentrates the overwrite workload on at most 1,000 keys; the default distributes it over the table's key range. This hot-key case is not a calibrated Zipf distribution.

For binaries built with failpoint support, `--pause-maintenance` pauses publication of background rewrites. Running both binaries this way separates query/publication cost from different compaction progress; confirm that the reported part counts match. This mode measures a controlled backlog and does not measure sustainable ingestion or space reclamation.

## Review follow-up {#review-follow-up}

The follow-up to commit `33b9962eb85` addresses the review findings without changing the durable format:

| Finding | Change |
| --- | --- |
| Per-query partition-version map construction | Lazy `call_once` cache per immutable catalog root, shared directly by queries |
| Repeated healthy-table scans | Complete-cycle idle backoff, publication wakeup, and a short cooldown for a healthy cycle with new publications |

| Cached full ranges destroyed while holding the parts lock | One old snapshot retained locally until after unlocking, including exception unwinding |

A shared decoded-mask cache would require a database-instance epoch in the cache key: generation numbers restart on reopen, so `(part UUID, generation)` alone would be unsafe across instances. ## Correctness follow-up to the second review {#correctness-second-review}

The follow-up to `eea2c8468d9` covers the following review items:

| Item | Resolution |
| --- | --- |
| 1: Native partition transfer can expose masked source rows | The shared structure check rejects unique-key sources, including transfers to `ReplicatedMergeTree`; upsert-to-upsert transfer retains its visibility-aware path. |
| 2: Multiple view sinks share a retry namespace | Dependent-view tokens use `DeduplicationInfo` source/view/block identities, with unit numbering local to that identity. Direct inserts retain the existing retry format. Disabled deduplication is respected. |
| 3: Tuple keys fail at insertion | Recursively flatten tuple elements for comparable encoding; normalize wrapped and sparse columns. |
| 4–5: A healthy prefix or an oversized part prevents expiration | A due or sufficiently masked source that does not fit the remaining budget starts an independent segmented rewrite. |
| 6: Interrupted native deletion leaves directories behind | Recovery removes well-formed `delete_tmp_` directories after checking that they do not name an active authorization; symbolic links remain errors. |
| 7: A fenced table breaks metadata introspection | Size introspection uses the last published accounting; user data reads remain fenced. |
| 8: Independent parallel-replica snapshots | Unsupported parallel-replica reads are rejected at snapshot acquisition and the legacy read entry point. |
| 9: Database background work races with table deletion | `DROP` releases the published snapshot and closes durable state before removing files. Remaining pinned snapshots cause an exception and preserve the files. |
| 10: Cleanup can fail after import publication | `ATTACH` schedules cleanup instead of running unrelated retirement cleanup on its success path. |
| 11: `SYSTEM STOP MERGES` does not stop maintenance | Stop before candidate scanning and wake maintenance when merge or TTL action locks are removed. |
| 12: Shutdown waits for a full rewrite | Check both shutdown and flush preparation between input blocks and output units; completed partial publications remain durable. |
| 14: Failed creation prevents retry | Validate resource settings before creating data directories or the manifest, and remove an exclusively created file if writing or syncing it fails. This does not cover every later database-metadata failure after successful storage construction. |

The view-token fix does not make source and dependent-view commits atomic. If an input chunk is partly committed at the source, source replay can filter those rows before they ever reach a view. If the source commits but the view fails, a retry can likewise omit rows from the target. These cases still require reconciliation; a successful retry alone is not evidence that every dependent target contains every source row. The regression for a failed source stream checks token stability for the later blocks, without assuming atomic recovery of already committed source blocks.

Items 13 and 15 remain separate work: handling dependent-view topology changes between asynchronous queue admission and flush, and legacy `parts_sync_v1` zero-filled-tail recovery. The current failure behavior is not replaced with a permissive recovery path. General cleanup after a later `CREATE` metadata failure, retired-mask cache eviction, and interrupted manifest-upgrade cleanup also remain open. No experimental setting gate is added: default-settings creation is an explicit requirement for this engine.
