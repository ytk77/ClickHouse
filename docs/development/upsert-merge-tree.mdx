# `UpsertMergeTree` development {#upsert-merge-tree-development}

New `UpsertMergeTree` tables use the v8 development-stage [disk-state protocol](/development/upsert-merge-tree-disk-state),
including a disk-backed winner index and automatic bounded merge and retirement. A successful synchronous
insert publishes one winner per partition-local unique key; reads do not require `FINAL`.
Journal grouping, native metadata paging and the complete production gates remain unfinished.

The parts-only persistence and capacity sections below describe the legacy `parts_sync_v1` protocol,
which remains supported for existing v7 tables. Its fixed capacity limits do not apply to new
`disk_state_v2` tables. Existing `MergeTree` tables retain their engine identity and ingestion behavior.

## Initial SQL definition {#initial-sql-definition}

`CREATE TABLE` with `UpsertMergeTree` does not require `allow_experimental_unique_key`.
The `UNIQUE KEY` clause is required and validated by the engine, including when the setting is disabled.

```sql
CREATE TABLE player_state
(
    tenant_id UInt64,
    player_id UInt64,
    ver UInt64,
    status String
)
ENGINE = UpsertMergeTree(ver)
PARTITION BY tenant_id
ORDER BY (tenant_id, player_id)
UNIQUE KEY (tenant_id, player_id);
```

The optional engine argument names one stored, non-null `UInt64`, `DateTime`, or `DateTime64` version column.
Omitting it selects the commit-order winner contract. Higher versions win; equal versions use
later commit order, then the original row position within the input block. Each insert supplies
a complete replacement row. Inserts execute synchronously automatically, including when the
session or user profile enables `async_insert`. Existing `INSERT` and `INSERT SELECT` statements
do not need an additional `SETTINGS` clause. Success is returned after the engine completes its
durable commit, even with `wait_for_async_insert = 0`. This also applies to inserts through
`Alias` tables and cascading materialized views whose destination is `UpsertMergeTree`.

`join_use_nulls` retains its ordinary query meaning. The engine requires neither a particular
value nor an explicit setting for `SELECT` or `INSERT SELECT`.

Time versions compare the stored instant, independently of the display timezone. `DateTime` has
second precision; `DateTime64` retains the column's declared precision from zero to nine fractional
digits, including times before the Unix epoch. Input conversion to the declared column type happens
before comparison. Updates at the same stored instant use the same commit-order tie breaker.
Stored `MATERIALIZED` version columns are also supported; `Nullable`, `LowCardinality`, and `ALIAS`
version columns are not.

```sql
CREATE TABLE account_state
(
    id UInt64,
    updatetime DateTime64(6, 'UTC'),
    value String
)
ENGINE = UpsertMergeTree(updatetime)
ORDER BY id
UNIQUE KEY id;
```

The unique key must contain stored columns with non-null integer, `String`, `FixedString`,
or nonempty tuple types recursively composed from these types. Key expressions currently
accept column identifiers; partition and sorting expressions must be deterministic.

The first implementation requires one local disk. It forces `assign_part_uuids`,
`fsync_after_insert`, and `fsync_part_directory` on, including during attachment.
The sink also synchronizes all payload files and directories before appending a composite terminal
record. The record is synchronized before part rename, directory synchronization and visibility publication.
The table manifest must exist during attachment and must match the schema and disk.
An existing data directory cannot be imported as a new `UpsertMergeTree` table.

Sampling definitions, streaming, `BACKUP`/`RESTORE`, `CHECK TABLE`, and background disk moves remain gated.
The supported partition, projection and incremental materialized-view operations are described below.
The `_upsert_` prefix is reserved; the input-only delete flag is not connected yet.
Partial-column updates remain unsupported; replace a row by inserting a new version.


## Incremental materialized views {#upsert-incremental-materialized-views}

An `UpsertMergeTree` table can be the source of an incremental materialized view:

```sql
CREATE TABLE events (id UInt64, ver UInt64, value String)
ENGINE = UpsertMergeTree(ver) ORDER BY id UNIQUE KEY id;

CREATE TABLE event_history (id UInt64, ver UInt64, value String)
ENGINE = MergeTree ORDER BY (id, ver);

CREATE MATERIALIZED VIEW events_mv TO event_history AS SELECT * FROM events;
```

The view processes incoming `INSERT` blocks, as with `ReplacingMergeTree`. It receives
submitted rows even when a version loses the source's winner comparison. Subsequent
upserts, `DELETE`, expiration, `TRUNCATE` and partition operations do not retract or
replay rows in the view target. An aggregate over this event stream therefore does not
automatically represent the source's current winners. Source and view targets do not
form a cross-table transaction. The standard
`wait_for_part_commit_in_dependent_materialized_views` setting is honored.

An explicit `insert_deduplication_token` replay does not forward previously committed
source units to dependent views. A partially replayed input forwards only newly
committed units, preserving their original deduplication identities. This also applies
when asynchronous insertion settings route the request to synchronous execution.
Source deduplication does not repair a view target after a failure between the source
commit and the target commit; such a target may need reconciliation or rebuilding.

## Partition management {#upsert-partition-management}

Tables using `disk_state_v2` support these operations:

```sql
ALTER TABLE partitioned DROP PARTITION 202609;
ALTER TABLE partitioned DETACH PARTITION 202609;
ALTER TABLE partitioned ATTACH PARTITION 202609;
ALTER TABLE partitioned ATTACH PARTITION 202609 FROM archive;
ALTER TABLE partitioned REPLACE PARTITION 202609 FROM archive;
ALTER TABLE partitioned MOVE PARTITION 202609 TO TABLE archive;
ALTER TABLE partitioned FREEZE PARTITION 202609 WITH NAME 'snapshot';
ALTER TABLE partitioned UNFREEZE PARTITION 202609 WITH NAME 'snapshot';
```

`DROP PART`, `DETACH PART`, `ATTACH PART`, `DROP DETACHED PARTITION/PART`, and the
`FREEZE`/`UNFREEZE` whole-table forms are also supported. Cross-table transfers require
two different `UpsertMergeTree` tables with matching physical columns, partition,
sorting and unique keys, and version column. Disk and volume moves remain unsupported
because this engine requires one local disk.

Imports read only visible source rows, prepare fresh immutable parts, and compare
imported versions with destination winners. Without a version column, imported rows
are newer writes. `REPLACE PARTITION` removes destination winners and retry tokens for
that partition before admitting the imported rows in the same durable batch. An empty
visible source is rejected unless `allow_replace_partition_from_empty_source=1` is set.
`DROP PARTITION` and `DETACH PARTITION` also clear partition retry tokens; a single-part
operation removes only winners belonging to that part and preserves partition tokens.
No masked historical row becomes a winner when its replacement is removed.

Each destination import or removal is published through one synchronized state batch.
The retirement and import state must fit the existing 128-MiB batch budget; exceeding
it rejects the operation before changing live data. Preparation pins a source snapshot
and allows concurrent inserts. Only the publication phase excludes inserts. Schema
changes and maintenance serialize with preparation on the participating tables;
unrelated tables can perform partition operations concurrently.
Removals retire the parts selected in that snapshot. Parts inserted afterward remain,
and their winner identities are checked at publication before comparing imported rows. Partition retry tokens are
cleared only if that partition's commit sequence has not changed since selection;
writes to other partitions do not prevent clearing them. Otherwise existing tokens
are retained to protect concurrent writes. Whole-partition removal uses a winner
range deletion and restores winners owned by surviving parts. Its state budget
depends on retirement metadata, token cleanup, imports and concurrent survivors,
rather than the number of old winners being removed. Exceptionally large survivor sets or imports can still
exceed the 128-MiB limit; the operation then leaves live data unchanged.

On an unversioned table, imported rows in `REPLACE PARTITION` are committed after
preparation. For the same key, they replace even an insert committed during preparation;
concurrent keys absent from the import survive. Versioned tables compare versions at
publication, so a newer concurrent version remains the winner.

`MOVE ... TO TABLE` commits the destination first, then removes the source. These are
two table commits: interruption between them can leave visible copies in both tables.
Inspect both tables before retrying an interrupted move, especially without versions.

Detached and frozen parts include a checksummed `upsert_visibility.bin` containing the
part identity, row count and visibility mask. Preserve this file when copying frozen
parts into `detached`. An `UpsertMergeTree` payload without this visibility file is
rejected on import. Ordinary native parts without Upsert lineage can be imported from
`detached`; all their physical rows are candidates. Consumed detached inputs have a
durable cleanup record, allowing restart to finish cleanup without importing them twice.
Importing existing Upsert lineage preserves the encoded key sizes admitted by the
source even when the current session has a smaller `unique_key_max_encoded_size`.

An interrupted `DETACH` may leave both an active part and its detached copy. `ATTACH`
rejects a detached identity that is still active. After the original identity has been
retired, importing a historical backup still counts as a new write; without versions,
inspect the backup before restoring it over newer data. If recovery finds both an
uncommitted `attaching_` directory and its original detached name, it preserves the
former under an `upsert_recovered_` name and logs a warning. This preserved copy
requires inspection and is excluded from automatic partition attachment.

To recover a preserved copy, inspect `system.detached_parts` and the warning log,
then choose which copy to retain. Pause partition-management commands while changing
files. Inside this table's `detached` directory, rename the selected
`upsert_recovered_<id>_<part>` directory back to `<part>` only when that name is free;
never overwrite the conflicting copy. Preserve every file, including
`upsert_visibility.bin`. Then run `ALTER TABLE table_name ATTACH PART '<part>'`.
The prefixed recovery name itself cannot be used as an `ATTACH PART` argument.

Failures while registering temporary parts, before the durable state write begins,
roll back registration and leave the table available for retry. An incomplete rollback
or an ambiguous failure after the durable state write begins still fences the table
until restart and recovery.

The first partition operation adds `partition_policy=state_v1` to the table manifest.
Older binaries reject this header; downgrade requires a compatible binary. These
operations are unavailable inside explicit transactions or on `parts_sync_v1` tables.

## Projections {#upsert-projections}

Projections can be declared in `CREATE TABLE` and managed with standard syntax:

```sql
ALTER TABLE events ADD PROJECTION by_value (SELECT * ORDER BY value);
ALTER TABLE events MATERIALIZE PROJECTION by_value;
ALTER TABLE events DROP PROJECTION by_value;
```

Both ordinary and aggregate projections are supported. `ADD PROJECTION` changes
metadata; subsequent inserts create the projection according to the normal
`materialize_projections_on_insert` policy. `MATERIALIZE PROJECTION`, optionally
`IN PARTITION`, rewrites existing visible rows and explicitly creates projections.
`DROP PROJECTION` retires obsolete projection payloads through immutable part rewrites.

A projection can reorder or aggregate rows, so parent row masks cannot be applied to
its output offsets. The optimizer uses projections for parent parts that are fully
visible in the query's pinned snapshot, and reads base data for parts with hidden rows
in the same query. Implicit count/minmax shortcuts require all selected parts to be
fully visible. Materialization or maintenance can make a parent eligible again by
removing hidden rows.
Explicit projection introspection rejects parent parts with hidden rows. Projections
that require commit-order block numbers are currently unsupported.

## Truncating a table {#upsert-truncate}

Tables using `disk_state_v2` support standard syntax without additional settings:

```sql
TRUNCATE TABLE current_state;
TRUNCATE TABLE IF EXISTS current_state;
```

`TRUNCATE` removes all rows across all partitions and preserves the table definition,
including defaults, keys, indexes, projections and `TTL`. It waits for active insert pipelines and
serializes with deletion, schema cleanup and maintenance. A single synchronized state
batch retires all active parts and clears winners, visibility masks, version floors and
insert deduplication tokens. Subsequent inserts can reuse previous keys and tokens,
including versions lower than those stored before truncation. An empty table can also
be truncated to reset retained tokens.

Readers that already pinned a snapshot may finish reading the previous data. New readers
see the empty state after publication; later inserts are processed normally. Part files
are reclaimed once readers release them. Recovery completes a durable truncation after
interruption, so retired rows do not reappear. If an exception occurs after the durable
commit, the table is fenced until restart and recovery; retrying after recovery is safe.

Truncation reads the part catalog without scanning row payloads. Retirement metadata must
fit the existing 128-MiB state-batch budget; exceeding it rejects the operation before any
data changes. Explicit transactions and the legacy `parts_sync_v1` protocol remain unsupported.

## Deletes, columns and indexes {#upsert-delete-columns-indexes}

Tables using `disk_state_v2` support the usual `MergeTree` syntax:

```sql
DELETE FROM current_state WHERE id = 42;
ALTER TABLE current_state DELETE WHERE id = 43;
ALTER TABLE current_state ADD COLUMN category String DEFAULT 'unknown';
ALTER TABLE current_state ADD INDEX category_idx category TYPE bloom_filter GRANULARITY 1;
ALTER TABLE current_state MATERIALIZE INDEX category_idx;
ALTER TABLE current_state DROP INDEX category_idx;
ALTER TABLE current_state DROP COLUMN category;
```

`DELETE` and `MATERIALIZE INDEX` also accept `IN PARTITION`. Deletes evaluate the predicate
against visible winners, and durably remove matching winners before returning. A concurrent insert
that replaces a selected row is preserved. As with expiration, deletion removes the version floor;
a later insert with a lower version can create the key again. Completed part operations survive
restart. A query affecting several rewrite units can complete some units before an exception or interruption;
the whole query is not an atomic transaction. Execution is synchronous even when
`lightweight_deletes_sync` or `mutations_sync` is zero.

Column and index changes use local `Atomic` or `Ordinary` database metadata. Standard column
defaults, `MATERIALIZED` and `ALIAS` expressions, placement clauses and conditional
`IF EXISTS` / `IF NOT EXISTS` clauses use the existing `MergeTree` validation rules.
Key columns, the version column and required expression dependencies cannot be dropped.
`ADD COLUMN` reads defaults for older parts. `DROP COLUMN` rewrites affected parts through the
engine's durable replacement protocol; reusing the name does not restore the dropped values,
including after interruption and restart. Schema publication waits for active insert pipelines.
Cleanup runs before acquiring and after releasing the schema write lock, so inserts can proceed
while obsolete payloads are rewritten. Cleanup only rewrites parts containing removed columns
or index payloads; adding a new index does not rewrite healthy existing parts.
When one statement drops and re-adds the same name, removal is committed before the new
definition; an interruption can leave the removal committed.

`ADD INDEX` applies to newly written parts; use `MATERIALIZE INDEX` to build indexes for existing
parts. Index removal and materialization replace authenticated parts without modifying their
files in place. These operations may read and rewrite existing data, so their cost depends on
table size. Rewrites stream output into units targeting 32 MiB and also bound row count,
lineage and pending state. A source part can produce several output parts, including when added
column defaults expand its data. An indivisible wide row can exceed the byte target and remains
subject to the query memory limit. Each unit durably relocates winners and masks their source
positions together. Sources remain readable until the final unit retires them; interruption can
leave completed units committed within a source part. The disk-state format is unchanged.

The first column or index alteration upgrades an older disk-state manifest to
`schema_policy=metadata_v1`. SQL metadata then owns mutable column and index definitions,
while the manifest continues to bind the disk, keys, version type and table incarnation.
Older binaries reject this manifest. The legacy `parts_sync_v1` protocol does not support these
operations.

## Background part size and prewarming {#upsert-background-part-size-prewarming}

For wide tables, larger background parts can reduce the number of files and marks opened by
aggregation queries. `upsert_maintenance_target_bytes` defaults to 32 MiB and accepts 32–256 MiB.
It applies to background maintenance; insertion units and foreground mutation output retain their
existing limits. Row, lineage and state budgets can split a background part before this byte target.

```sql
ALTER TABLE current_state MODIFY SETTING
    upsert_maintenance_target_bytes = 134217728,
    prewarm_mark_cache = 1,
    columns_to_prewarm_mark_cache = 'id,value';
```

Existing parts converge gradually, requiring rewrite I/O and memory that can be several times the
target. Prewarming uses marks retained by the writer after successful publication; failures do not
change the durable result. It does not warm all data pages. Defaults remain unchanged.
See [query part size and cache prewarming](/development/upsert-merge-tree-scalability#query-part-size-prewarming)
for the supported settings, memory and waiting behavior, restart convergence and downgrade limits.

## Row expiration {#upsert-row-expiration}

New `disk_state_v2` tables support table-level `TTL ... DELETE`, including `DELETE WHERE`:

```sql
CREATE TABLE expiring_state
(
    id UInt64,
    ver UInt64,
    updated_at DateTime,
    value String
)
ENGINE = UpsertMergeTree(ver)
ORDER BY id
UNIQUE KEY id
TTL updated_at + INTERVAL 30 DAY DELETE;
```

Expiration runs asynchronously in bounded background maintenance, including when the table has
only one part and no new inserts arrive. A row can remain visible after its deadline until
maintenance commits. `Date`, `Date32`, `DateTime` and `DateTime64` expressions use the standard
`MergeTree` expiration semantics. `SYSTEM STOP TTL MERGES` pauses expiration;
`SYSTEM START TTL MERGES` resumes it. The native `merge_with_ttl_timeout` setting does not
control this engine's dedicated maintenance task.

Expiration applies to the current winning row. If another insert replaces that row while maintenance
is preparing, the new winner survives and is evaluated by subsequent maintenance. Readers already
holding a snapshot keep their original rows. The winner-index deletion and part retirement commit
atomically and survive restart; superseded physical rows cannot reappear.

Once a winner expires, its key has no retained version floor: a subsequent insert can create it again,
even with a lower version. Existing deduplication tokens still suppress retries during their normal
retention window. Retention policies must account for late arrivals and retries outside that window.

### Changing expiration on existing tables {#upsert-alter-row-expiration}

Existing `disk_state_v2` tables in local `Atomic` or `Ordinary` databases support adding, changing,
and removing table expiration without recreating the table:

```sql
ALTER TABLE expiring_state MODIFY TTL updated_at + INTERVAL 7 DAY DELETE;
ALTER TABLE expiring_state MODIFY TTL updated_at + INTERVAL 30 DAY DELETE WHERE value = 'inactive';
ALTER TABLE expiring_state REMOVE TTL;
```

`MODIFY TTL` applies to existing rows and subsequent inserts. The statement commits the new policy;
bounded background maintenance then recalculates existing parts and deletes eligible winners.
It does not wait for all expired rows to disappear. This uses the engine's maintenance protocol,
independently of `materialize_ttl_after_modify`, and creates no native mutations. Changing only the
`WHERE` condition also invalidates cached expiration information. Pausing `TTL` merges postpones
this work until they resume.

`REMOVE TTL` stops future expiration, including any maintenance prepared under the previous rule
that has not committed when the policy changes. It cannot restore rows already deleted. Extending
the retention period similarly protects remaining rows from pending work under the old rule.
In-flight inserts retain their original metadata snapshot; maintenance detects their old policy and
reevaluates them under the current rule.

The first alteration atomically upgrades older disk-state manifests to support mutable policies.
The database metadata file is then the durable authority for `TTL`; the manifest continues to
authenticate the fixed column and key structure. Restart uses the committed SQL policy. An ambiguous
metadata commit fences the table until restart. Binaries without mutable-policy support reject the
upgraded manifest, so a downgrade requires a compatible binary. Editing metadata files directly is unsupported.

`parts_sync_v1` tables and replicated database metadata are not supported by these alterations.
`MATERIALIZE TTL`, column expiration, `TO DISK`, `TO VOLUME`, `RECOMPRESS`, `GROUP BY` and
`ttl_only_drop_parts=1` remain unsupported. `ADD/DROP COLUMN` and `ADD/DROP INDEX` are supported as described above. Other schema alterations remain gated.

## Row metadata version 1 {#row-metadata-version-1}

All integer fields are little-endian. The encoded index value is 42 bytes without a version
and 50 bytes with one. It has no relationship to the `Native` wire format.

| Field | Bytes | Meaning |
| --- | ---: | --- |
| Magic | 4 | ASCII `UMRV` |
| Version | 1 | `1` |
| Flags | 1 | Bit 0: application version present; bit 1: `SELF` activation binding |
| Row offset | 4 | Physical row position, strictly below `2^28` |
| Operation identity | 16 | Two 64-bit limbs; the all-zero identity is invalid |
| Block ordinal | 8 | Position in the original logical input unit |
| Write CSN | 8 | Original write sequence; zero only for `SELF` |
| Application version | 0 or 8 | Present only when flag bit 0 is set |

The table incarnation and partition scope come from the authenticated enclosing manifest.
`SELF` must resolve through the producing part's activation binding before comparing winners.
A resolved row retains its original write CSN through later drain, merge, and index rebuild.
The eight-byte application version is an order-preserving unsigned value: `UInt64` is unchanged,
`DateTime` uses zero-extended epoch seconds, and `DateTime64` uses the underlying signed ticks
converted to `UInt64` with bit 63 flipped. This retains negative-time ordering without rescaling
or losing fractional precision. The authenticated table schema fixes the version type and scale.
Existing `UInt64` metadata and table manifests remain unchanged. Older binaries reject tables
using time version columns during schema validation. The `Native` wire format is unchanged.
Winner comparison orders `(version, write_csn, block_ordinal)`, or `(write_csn, block_ordinal)`
without an application version. Comparing different version modes or unresolved rows is an error.
Legacy four-byte SST values are rejected by this decoder. New parts persist these values in the
SST index and in the checksummed `upsert_rows.bin` lineage sidecar. Other engines retain their legacy format.

## Terminal-record envelope version 1 {#terminal-record-envelope-version-1}

All integers are little-endian. Total frame length is bounded to 64 MiB before allocation.

| Field | Bytes | Meaning |
| --- | ---: | --- |
| Magic | 8 | ASCII `UMTLOG01` |
| Version | 2 | `1` |
| Kind | 1 | Operation discriminator |
| Reserved flags | 1 | Must be zero |
| Total frame length | 4 | Includes prefix and trailing CRC |
| Header CRC-32 | 4 | Covers the preceding 16 bytes; validates the length before accepting a torn tail |
| Table incarnation | 16 | Nonzero table identity |
| CSN | 8 | Nonzero, strictly increasing within the partition |
| Previous frame hash | 16 | Two limbs of `SipHash`-128 over the entire preceding frame |
| Operation identity | 16 | Nonzero operation identity |
| Partition identifier length | 4 | Between 1 and 1024 bytes |
| Partition identifier | Variable | Exact identifier bytes |
| Payload | Variable | Operation-specific contents |
| CRC-32 | 4 | Covers every preceding byte of the frame |

The numeric kinds are `UPSERT=1`, `DELETE=2`, `NOOP=3`, `PART=4`, `DRAIN=5`,
`MERGE=6`, `MUTATION=7`, `MATERIALIZED=8`, and `CHECKPOINT=9`.
Recognizing a kind in the envelope does not enable its execution.
`PART` and `NOOP` have versioned composite payloads. Other operation payloads and the
checkpoint-generation protocol are not implemented.

An empty replay boundary has CSN zero and an all-zero preceding hash.
Recovery validates identity, partition, sequence order, and the hash chain, without searching
past an invalid frame. Complete frames with bad checksums are errors even in an unsealed suffix.
Only a truncated final frame may be discarded when the caller explicitly permits an unsealed tail.
Sequence overflow is an error before append.

## Commit and recovery protocol {#commit-and-recovery-protocol}

`PartitionLog` provides exclusive file ownership, bounded synchronous append, complete-prefix
recovery and fencing after ambiguous write or sync failures. A durable registry discovers partition
logs. The table manifest binds the schema, disk and `parts_sync_v1` protocol before part discovery.
Required missing files are errors, never empty bootstrap state.

A composite `PART` record authenticates the producing UUID, temporary and final part names,
the complete immutable file inventory, incoming-loser mask, incumbent kills and retry token.
The input is folded before native sorting while retaining its original row ordinal. Commit publication
pins the active parts and immutable deletion masks under the same parts mutex. Existing readers
retain their previous masks. Count, query-condition-cache and implicit projection shortcuts are gated.
An input unit with no winning rows appends a `NOOP` decision.

Recovery precedes native part loading. It validates the log chain, file hashes and row lineage,
recomputes winner decisions and completes authorized temporary-part renames. Missing payloads,
changed files and unauthorized final parts fail attachment. Native dense-index repair is disabled
because it cannot recreate the versioned lineage. Ambiguous commit failures fence reads and writes
until restart and recovery.

`insert_deduplication_token` identifies each bounded input unit within each partition. An identical retry
retains its original result, even after a newer update. Reusing the token with different evaluated
input fails. Retries must preserve block boundaries and input values. Atomicity is per partition
and input unit; a query containing several units can partially commit. Oversized blocks are split
automatically using the [shared sink's bounded-input policy](/development/upsert-merge-tree-disk-state#disk-state-automatic-input-splitting).

## Resource bounds and remaining gates {#resource-bounds-and-remaining-gates}

This development stage retains every authorized part and terminal record. Background merges,
cleanup, moves, journal publication, drain, group commit, checkpoint rotation and index rebuilding
are disabled. Admission fails at the following bounds; no automatic reclamation is available:

| Resource | Bound |
| --- | ---: |
| Retained parts per table | 4,096 |
| Partitions per table | 512 |
| Live keys per partition | 262,144 |
| Encoded live-key bytes per partition | 64 MiB |
| Retained retry tokens per partition | 4,096 |
| Log file | 256 MiB |
| Internal input unit (larger blocks are split) | 1,048,576 rows and 32 MiB |
| Token text | 1,024 bytes |

The coordinator copies bounded in-memory key state and masks during preparation. The table-wide
limits permit larger hash-partitioned imports while retaining the per-partition key and byte limits.
These admission limits do not reserve memory; provision server memory for the retained key state
and concurrent preparation before large imports. It is intended
for correctness validation, with no production throughput or full v7.1 acceptance claim. The current
manifest protocol is incompatible with the earlier ingestion-disabled scaffold; validation deployment
uses a fresh data directory and preserves the previous release.
