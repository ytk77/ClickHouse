# `UpsertMergeTree` v8 disk state {#upsert-disk-state}

This is an implementation-stage protocol, not a production-readiness declaration. The complete target remains the [continuous-ingestion design](/development/upsert-merge-tree-continuous-ingestion). Existing `parts_sync_v1` tables retain their original state store and limits. New tables identify their protocol as `disk_state_v2`; older binaries must reject that manifest. No in-place conversion of existing tables is performed.

## Commit authority {#disk-state-commit-authority}

One local `RocksDB` database in `upsert_state_v2` holds the table's durable decisions. Its synchronous `WriteBatch`, including its `WAL`, is the sole terminal commit authority. There is no independently committed partition log. The storage database's atomic manifest installation, memtable flush and compaction manage its checkpoint and log lifecycle.

The table incarnation and protocol are persisted inside both the authenticated table manifest and the state database. `ATTACH` requires both and never creates a replacement state database. Recovery uses absolute-consistency `WAL` replay and propagates errors; it does not skip damaged records or fall back to an older application checkpoint.

1. Write and synchronize the immutable temporary part, checksums, lineage, and parent directory.
2. Under the table parts lock, read only the batch's incumbent keys; build winner changes, visibility masks, part authorization, token result and next partition sequence. Preallocate the next read version, containing the resulting native parts, visibility state and part statistics.
3. Apply one synchronous database write batch. Its durable completion authorizes the temporary payload even if the process stops before rename.
4. Pin the resulting database snapshot, rename the part and synchronize the directory. Finish native part activation and retirement under the parts lock, then atomically replace the published read version through a separate, short publication mutex.
5. Acknowledge only after publication. An ambiguous state write or failure after authorization fences new reads and writes until restart and recovery. Already acquired read versions remain consistent.

## Insert preparation and batching {#disk-state-parallel-preparation}

`max_insert_threads` controls part preparation within one ordered sink. Its effective concurrency also respects `max_threads` and the corresponding minimum-free-memory settings, and is capped at eight in-flight parts per query. The queue counts both running preparations and completed parts awaiting publication, with an additional 128-MiB budget for their input blocks, including internal ordinals. Part metadata, encoded indexes and compression buffers consume additional query-accounted memory within the existing per-unit limits. Setting `max_insert_threads=1` prepares and commits each part synchronously.

The sink assigns token units before dispatch, validates and folds all partitions of an input block, and publishes completed preparations in the original block and partition order. Workers only create temporary durable payloads; they never publish winners. Input completion drains the queue before success. On cancellation or an exception, outstanding preparations are joined and discarded without committing later units. Previously committed units retain the existing partial-insert and retry semantics. The engine continues to reject multiple independent sink chains, so retry identities and equal-version winner order do not depend on worker completion order.

Immutable input lineage, offset and key uniqueness checks run before the commit lock. Foreground winner lookup and maintenance relocation use bounded `RocksDB` `MultiGet` batches of at most 1,024 keys. Writers remain serialized under the table parts lock; multiple SQL partitions do not bypass it. Readers acquire the published version without that lock. Missing keys are valid for new inputs, while missing maintenance winners and database errors remain exceptions.

For throughput tuning, compare input batches around 16K, 64K and 256K rows and two to four concurrent clients against the same workload. The input block must also fit the 32-MiB limit; wide rows require smaller row batches. Keep key-to-partition routing stable and measure both initial ingestion and sustained overwrites with maintenance enabled. Increasing concurrency can increase memory, temporary disk usage and commit-lock waiting, and need not increase throughput.

For a multi-block `INSERT SELECT`, an initial session configuration is:

```sql
SET max_threads = 4;
SET max_insert_threads = 4;
SET max_block_size = 65536;
SET max_insert_block_size = 65536;
SET min_insert_block_size_rows = 65536;
SET min_insert_block_size_bytes = 0;
```

Measure this against `max_insert_threads=1` using identical input blocks. A single small input block in one SQL partition only produces one preparation task. The repository's `utils/upsert-benchmark/run.py` compares multi-block requests, independent clients and batch sizes, checking visible results after every phase.

## Keys and values {#disk-state-encoding}

All integer fields are unsigned little-endian. Length-delimited strings use a four-byte length. The prefix contains a one-byte namespace followed, where specified, by a length-delimited SQL partition identity. Encoded unique keys retain the existing full key equality and are not replaced by hashes.

| Key | Value |
| --- | --- |
| `identity` | Protocol plus table incarnation |
| `part_count` | Eight-byte authorized part count |
| `C`, partition | Eight-byte last committed partition sequence |
| `W`, partition, encoded key | Physical part identity plus length-delimited `IndexValue`, including the original resolved winner tuple |
| `A`, final part name | Versioned `PartCommit`, authenticating the immutable payload |
| `M`, printable part identity | Checksummed serialized `DeleteBitmap` |
| `T`, partition, token, unit | Payload hash, original accepted-row count (including zero), and eight-byte expiration time |
| `O`, printable operation identity | Original commit sequence |
| `R`, retired part name | Original authorization, permitting physical removal once native reader pins are released |
| `E`, big-endian expiration time, token key | Ordered retry expiration entry |
| `retry_bytes` | Accounted retry-state bytes |

Namespace boundaries and length delimiters prevent ambiguous keys even when user strings contain zero bytes or separators. Per-record decoder and row-offset bounds remain; they do not impose a partition's total key capacity. Counter overflow is an explicit exception.

## Working set and snapshots {#disk-state-working-set}

There is one state database per table, with a block cache, bounded write buffers, a bounded open-file cache, and shared background maintenance threads. There is no per-partition open log or resident winner map. A write batch contains only affected keys and masks; it does not clone the partition's historical index.

Readers pin a database snapshot together with their native parts. A mask lookup reads that exact sequence, including after newer updates or database flushes. Snapshot ownership keeps the database alive until readers release it. Attach iterates part authorizations without constructing a second full in-memory authorization map and verifies the immutable payloads before native loading.

Read publication uses MVCC: while a writer prepares, synchronizes or renames its payload, new queries can acquire the previous fully published version. The native part ranges and matching database snapshot switch together, so a reader cannot combine new masks with old parts. The publication mutex only copies or swaps a shared pointer; allocation, filesystem I/O and destruction of old versions run outside it. The empty mutation snapshot also avoids the parts lock because this engine rejects mutations and patch parts. This is statement snapshot visibility, not support for explicit SQL transactions.

Part ranges and their metadata statistics are built once per published part-set change and shared by readers. Column and index size totals are updated for added and retired parts before publication, so query planning, including column selection for `count`, does not reacquire the parts lock. Subcolumn size inspection also uses pinned published parts. This removes per-query full-catalog construction, but publication still eagerly constructs the new catalog. Old versions retain referenced parts and database snapshots until readers release them. Physical I/O contention and long-lived reader pins still require resource management; MVCC removes the durable writer's mutex from snapshot acquisition, not all possible sources of read latency.

## Automatic maintenance {#disk-state-automatic-maintenance}

The disk-state protocol schedules a dedicated table maintenance task, with ordinary native merges still disabled. It selects bounded same-partition units for small-part consolidation or rewriting parts whose dead-row fraction is at least one quarter. It reads sources through native sequential readers, materializes internal column wrappers before concatenation, and writes an immutable native part carrying the original resolved row lineage.

Selection budgets both uncompressed column bytes and the encoded lineage sidecar. The sum of source `upsert_rows.bin` payload sizes, excluding each source's 16-byte envelope, must fit within 64 MiB minus the output envelope. Resolving `SELF`, changing offsets and sorting preserve encoded row widths; filtering can only reduce that bound. The existing column and row budgets remain in force. Healthy parts larger than half of any output budget are treated as complete parts rather than repeatedly selected for an oversized merge. For example, two versioned 524,288-row parts with eight-byte keys remain separate because their combined lineage would require 66 MiB plus an envelope; subsequent small parts can still consolidate.

Each task resumes after the last selected source in native part order and wraps at the end. Selection does not restart unconditionally at the first partition, including after a failed attempt. Encoding errors and corrupted source metadata still propagate to the maintenance error log; the selector does not suppress them or raise the format's byte limit.

At commit, each currently live source identity must map to the same output identity. A source row superseded during the build is marked dead in the output. Missing, invented or duplicated identities are exceptions. Winner positions change without changing their original version, write sequence or ordinal. The atomic database batch replaces source authorizations with output authorization and retirement records; a fully dead input can produce no output.

Native part retirement completes before publishing the new read version. Native reference counting protects readers of earlier versions. Physical deletion precedes forgetting the retirement record. After process restart, prior reader pins no longer exist, and the durable retirement record authorizes completing interrupted deletion before native loading. Recovery validates the active payloads and masks before reclamation; it also removes uncommitted engine preparations after rolling forward all authorized payloads. The active catalog no longer requires deleted historical payloads to recover.

Tokens retain their result for 86,400 seconds according to the server clock. A one-GiB accounted retry budget rejects new token state rather than expiring valid tokens early. The background task removes expired entries in bounded batches and protects a newer reuse of the same token from an older expiration entry. Operation bindings are retained for active parts and removed atomically with their retirement; merged rows already contain resolved original lineage. No-op writes do not allocate permanent operation bindings.

These initial resource budgets are implementation defaults, not configurable SQL settings: 64-MiB index block cache, three 16-MiB write buffers, 128-MiB pending database batch, one-GiB free-disk maintenance reserve, and bounded maintenance input units. Foreground mask updates process one affected source at a time. Budgets limit current work or retained retry promises, not total partition or live-key counts.

## Remaining production gates {#disk-state-remaining-gates}

This implementation still uses native eager part metadata and synchronously creates one part per accepted request unit. Maintenance uses a bounded in-memory mapping; it does not yet split oversized sources or spill that mapping to disk. Large sources beyond its operation budget are skipped. Some source verification and index relocation run under the commit lock. These are explicit limitations, not evidence that all continuous-ingestion workloads are production-ready.

The full v8 release still requires grouped payload segments and drain, configurable workload and maintenance budgets, fair resource admission under overload, paging of native part metadata, large-source splitting/spill, bounded snapshot-age policy, and the full fault/concurrency/soak gates in the design. Backup, replication and in-place migration remain gated. Removing a count limit does not remove these requirements.
